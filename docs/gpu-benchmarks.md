# GPU benchmark: `xgboost_rs` against XGBoost `gpu_hist`

Run on a Google Colab **Tesla T4** (15 GB, 2 vCPU, 12 GB RAM), XGBoost 3.4.0,
`xgboost_rs` built `--release --features cuda`, via `tools/compare_gpu.py`.
Both sides train on the same generated bytes with the same parameters; each
trains once per case, because repeating the fit would let XGBoost reuse the
binned matrix it caches on the `DMatrix` while this crate rebuilt it.

## Result

**This crate still loses, by 5× to 14×.** `speedup` is XGBoost's time over
ours, so below 1.00 is a loss. `before` is the same measurement prior to the
per-level batching in `27ab94d`.

Accuracy is unchanged and comparable throughout — train RMSE within ~2% of the
reference, identical to 7e-5 on `lossguide`. The two sketch quantiles
differently, so exact agreement is not expected; `max_bin 64` is the widest gap
at 17%, where a coarse sketch has the most room to differ.

## What the batching bought, and what it did not

Batching a level's histogram builds and subtractions into one launch each
(`27ab94d`) was predicted to be the largest of the four costs. That was **right
about the mechanism and wrong about its weight in most cases**:

- `depth 10` improved **3.3×**, from 17.05 s to 5.12 s. That is the case with
  by far the most nodes, and it is now the *best* row in the table rather than
  the worst. The per-node launch overhead was real and it dominated there.
- Everywhere else the gain is 1.0×–1.3×. Node counts are an order of magnitude
  lower, so there was much less launch overhead to remove.
- `depth 4` and `max_bin 64` came out **slower** (0.80× and 0.94×). These are
  single runs, so some of that is noise, but there is a plausible mechanism:
  the batched grid is sized for the *widest* node in the level and launched for
  every node, so a level mixing one large node with several small ones now
  starts blocks that exit immediately. Per-node launches were right-sized.
  Sizing the grid per node within the batch would fix it.

The flat ~5 s floor across most rows, largely independent of rows, features and
bins, says the remaining cost is **not** proportional to the work. That points
at the per-level host round trips rather than at the kernels.

## Where the time still goes

1. **Three host round trips per level.** Down from five: the split evaluation
   now packs its results into two buffers, but each is still a full pipeline
   drain, and the partitioner reads its left counts for a third. Getting to one
   — or to none, by keeping the segment table on device — is the next thing to
   try, and the flat floor above is the evidence for it.
2. **The ELLPACK was uncompressed** when this was measured: four bytes per
   entry against XGBoost's bit-packed ~1 byte at 256 bins, so the hottest
   kernel moved 4× the memory it needed to, which is what should have mattered
   most at `rows 1M`, the row that improved least (1.01×). It is now
   bit-packed on device (`gpu::ellpack::pack_bins`, 8 bits for 256-bin data,
   9 with a missing sentinel) on every runtime with planes — but that has not
   been re-measured on a GPU yet, only tested for correctness at forced widths
   on the CPU runtime, where packing is deliberately off because it costs more
   instructions than it saves bytes there.
3. **The batched grid is sized for the widest node**, which costs the shallow
   cases (see `depth 4` above).

## Reproducing

```bash
cargo build --release --features cuda --bin train_bench
python tools/compare_gpu.py --binary target/release/train_bench
```

Add `--cpu` to time `device=cpu` alongside. Do not read CPU numbers from a
Colab VM: it has 2 vCPUs, so a CPU baseline there says more about the VM than
about either implementation. The same 2 vCPUs make a `--features cuda` build
take ~35 minutes, most of it in `tracel-rspirv` and `wgpu`.
