# GPU benchmark: `xgboost_rs` against XGBoost `gpu_hist`

Run on a Kaggle **Tesla T4** (15 GB, 4 vCPU Xeon @ 2 GHz), XGBoost 3.4.0,
`xgboost_rs` built `--release --no-default-features --features cuda`, via
`tools/compare_gpu.py` inside `tools/kaggle/run_gpu_compare.py` (see
`KAGGLE.md`). Both sides train on the same generated bytes with the same
parameters; each trains once per case, in its own process, because repeating
the fit would let XGBoost reuse the binned matrix it caches on the `DMatrix`
while this crate rebuilt it.

## Result (2026-09-05 pass)

`speedup` is XGBoost's time over ours, so above 1.00 is a win. Three tables,
because a process's first CUDA use is a cost of its own: on this VM the
driver takes 355 ms to create the primary context, and XGBoost's Python
process pays that at `import`, outside its timer, where this crate's binary
would pay it inside the fit. The **warm** table (`compare_gpu.py --warm`)
fits once before the clock on both sides, which is what any process that
fits more than once sees. The **cold** table times one fit per fresh process
on both sides, with the crate's binary starting the driver's context
creation on a thread before it generates its data (`--prewarm`, the
accounting the Python side gets from `import`) — and, in the last column,
without that, which is what a script that has its data ready before it
touches the device pays.

Accuracy: train RMSE within 0.03%–1.3% of the reference on every case (the
device sketches exact quantiles, closer to XGBoost's own device sketch than
the host summary was), and the same fit repeated sixteen times in one
process gives the same model every time.

### What a fit is made of now

Per-phase wall clock of the baseline case on the T4, kernel cache warm
(`XGB_PHASES=1`; CubeCL's per-kernel profile for the kernel times):

| | ms | notes |
|---|---:|---|
| CUDA primary context | 355 | the driver, once per process; on a thread from `gpu::warm_up`, overlapping the data load |
| first fit of a process, beyond the second | ~130 | the wait for that thread, each kernel's first module load, the memory pool's growth |
| matrix upload + device sketch + binning | 25 + 25 + 9 | was 1.44 s on the host; sparse 20 + 25 + 19 |
| one round, steady state | ~7 | root 1.3, level histograms 2.2, partition 1.3, evaluate 0.9, quantise 0.2, metric 0.2; gradients and the prediction update are on the device |
| **all kernels of one round** | **7.4** | the histogram kernel is 4.9 of them, 49 launches |

The histogram kernel, split by `bench`'s probe shapes: 9.9 Gentry/s as it
is, 22.3 without its shared-memory atomics, 22.9 without the bin decode as
well — the u32-carry accumulation is half its time, the decode nothing.

### What the pass changed, in the order it mattered

1. **The histogram grid** (`hist_kernel`). The grid was sized for the widest
   node of a level — up to 1 024 cubes per feature group — and launched for
   every node, and every cube of the shared-memory path zeroes 48 KiB and
   flushes ~3 000 bins with global atomics whether it had rows or not. That
   was the flat, size-independent floor the previous measurement saw. Each
   node now gets its own cube count, capped at two per SM, and the flush
   skips empty bins. The T4 tune sweep (`XGB_GPU_TUNE`) then found every
   remaining knob — block width, cap, shared budget, global path — within
   noise.
2. **NVRTC.** CubeCL's CUDA runtime compiles every kernel variant on its
   first launch — 40–250 ms each, ~1.8 s of a cold fit — and only caches the
   result on disk when told to. `gpu::default_client` now turns the cache on
   (`XGB_NO_KERNEL_CACHE=1` for the cold number: 3.63 s against 1.81 s warm
   on the baseline case).
3. **Setup on the device.** The host sketch (537 ms), host binning (611 ms)
   and pack + upload (336 ms) together cost more than XGBoost's whole fit.
   The values go up once; `gpu::sketch` sorts each column on the device (LSD
   radix, four 8-bit passes) and reads the cuts off the sorted column with
   the same rank queries the host makes against its summary — exact where the
   host's is a pruned approximation, so the two are not bit-identical and
   the parity tests pin the host sketch (`force_host_sketch`). One kernel per
   layout then bins and packs straight into the packed ELLPACK.
4. **Per-round host work off the host.** The gradient quantiser's three
   passes and its 8 MB `i64` upload (9 ms a round, 44 at a million rows) are
   three kernels and two readbacks of a few kilobytes.
5. **The partitioner's tile prefix** summed a segment's tile counts with one
   serial loop per cube — quadratic in the row count, 1.5 ms per level at
   500 000 rows and 5 ms at a million against 70 µs for the count pass.
   Cooperative now: 8–11 ms per tree became 2.
6. **Uploads.** Per-level tables (ten in the partitioner, six in the
   histogram build, five in the subtraction, six in the evaluator) are one
   packed upload each (`gpu::tables`). The runtime's own upload path moved
   memory at 0.36 GB/s on this VM by every route, where PyTorch moved it at
   4.4 GB/s pageable (`tools/kaggle/h2d_probe.py`), so uploads go through
   the driver directly (`gpu::tables::cuda_direct`, a `cuMemcpyHtoD` into
   the buffer's pointer with the device's primary context bound): the 100 MB
   matrix 308 → 24 ms, the round's gradients 3.2 → 1.6 ms. One trap in it,
   found by fitting the same case sixteen times in one process (run #23:
   three of eight 20-feature fits ended at a different model): a pageable
   `cuMemcpyHtoD` returns once the bytes are staged, not once the DMA has
   landed, and the runtime's stream is non-blocking, so the next kernel
   could read a per-level table early. A `cuCtxSynchronize` after the copy
   closes it at no measurable cost (run #24: sixteen identical fits, and
   the warm 20-feature RMSE is the cold one again).
7. **Host passes in parallel.** The regression objective's gradient and the
   elementwise metric reduction were serial loops; both now run in fixed
   4 096-row blocks (the same result at any thread count).
8. **The round on the device.** With the tree there, what remained on the
   host each round was the gradients, the prediction update — which read
   the row index back to do it — and the metric: 4.7 ms of a 16 ms round on
   the VM's four cores. `gpu::objective` keeps the predictions on the device
   for as long as every round can be done there (`reg:squarederror`, one
   output, one tree a round, no sampling or DART), computes the gradients,
   adds the leaves' values through the partitioner's row index, and scores
   `rmse` in the host's own 4 096-row blocks; the host copy comes back only
   when something host-side asks for it. The round is 16 → 9.8 ms, and the
   device fit is bit-identical to the CPU fit still. It also exposed a gap
   in the host route: a queued node that failed `min_split_loss` or the
   leaf budget was dropped without a leaf segment, so its value never
   reached the prediction cache; every leaf is recorded now.
9. **Measured and rejected on the T4.** 64-bit shared-memory atomics in the
   histogram: as `Atomic<i64>` the sums were wrong (cubecl 0.10 emits a
   signed `atomicExch` for the zeroing that CUDA has no native form of); as
   `Atomic<u64>` they are exact and **slower** — 4.2 against 9.9 Gentry/s,
   the fit 0.40 s against 0.33 — which is the reason upstream's carry scheme
   exists (`hist_smem64`). A contiguous-items tile loop (8.6 Gentry/s;
   `hist_contig`), the global-memory histogram path (level with shared),
   block widths and shared budgets (noise). One cube per SM beat two by ~8%
   in two sessions and is the default.

10. **The second pass over what remained (runs #25–#27).** The phase log and
    the per-kernel profile of a steady-state round disagreed by 4 ms of 11:
    the root step was 3.9 ms for 1.1 ms of kernels. Its 2 MB row index
    was built on the host and uploaded every tree (a kernel writes it now),
    and every per-level table went through the direct copy — which drains
    the queue before it and waits for its DMA after, two idle gaps a table,
    four tables a level — where the runtime's own stream-ordered write
    costs microseconds; the direct route now takes only uploads of a
    megabyte or more. The metric's 4 096-row blocks were summed by one
    unit each (0.74 ms a round): the block is sixty-four interleaved lanes
    now, on the host and the device alike, so the fit is still
    bit-identical to the CPU fit. Round 9.8 → 7 ms; the setup lost the
    second upload of the matrix (the sketch's copy is handed to the grower:
    25 ms dense, 53 ms CSR) and the feature-major bin+pack, which searched a
    CSR row per cell with the rows a warp apart (48 of 66 ms with 30% of
    the cells missing, 15 of 23 dense) and is a transpose of the packed
    row-major matrix now (1.3 ms). The loss-guided tree builds two
    histograms a batch and was zeroing a two-slot buffer for each; slots
    come from a buffer of sixty-four zeroed once, and the segment a batch
    splits is read from whichever row buffer holds it rather than copied to
    the front first. Cold start: `gpu::warm_up` begins the driver's
    context creation on a thread at program start — `train_bench
    --prewarm`, `compare_gpu.py --prewarm` — so it overlaps the data build
    as it overlaps `import` in a Python process; what a process still pays
    once is ~130 ms (the wait for that thread when the data build is
    shorter than the context creation, each kernel's first module load,
    the memory pool's growth).

Correctness held throughout: the CUDA kernel oracle, `tests/kernels.rs` and
`tests/gpu_training.rs` pass on the T4, and `compute-sanitizer` reports no
errors — it is what found the one CUDA-only fault, a `||` whose right operand
CubeCL evaluates unconditionally.

### Where the time still goes

1. **The histogram kernel's accumulation**: four shared-memory atomics with
   returned values per entry, half the kernel, and the kernel is two thirds
   of a round's kernel time. Native 64-bit shared atomics are slower still
   on this card (above), so the remaining levers are the ones upstream uses
   — a wider block per SM, fewer bins per group in flight — or a different
   accumulation altogether (per-warp privatisation, which trades contention
   for a reduction).
2. **Setup** is a quarter of the warm fit: the 100 MB matrix's upload
   (25 ms, pageable; pinned staging would be three times faster but
   page-locking 100 MB costs 460 ms once) and the radix sort's four passes
   over 25 M keys (21 ms).
3. **Loss-guided growth** expands one node a batch, as upstream does, so a
   64-leaf tree is 63 sequential steps of six launches and two readbacks
   each, ~0.3 ms a step against ~0.02 ms of kernel work: launch latency.
   Fusing the subtraction into the evaluation, or the two evaluation
   kernels, is the next step there.
4. **Cold start** in a process whose data is ready before the driver's
   context is (the 355 ms are the driver's; XGBoost's process pays them at
   import), plus the first module load of each kernel.

## Before this pass (Colab T4)

Run on a Google Colab **Tesla T4** (15 GB, 2 vCPU, 12 GB RAM), XGBoost 3.4.0,
`xgboost_rs` built `--release --features cuda`, via `tools/compare_gpu.py`.

### Result then

**This crate lost by 5× to 14×.** `speedup` is XGBoost's time over
ours, so below 1.00 is a loss. `before` is the same measurement prior to the
per-level batching in `27ab94d`.

Accuracy is unchanged and comparable throughout — train RMSE within ~2% of the
reference, identical to 7e-5 on `lossguide`. The two sketch quantiles
differently, so exact agreement is not expected; `max_bin 64` is the widest gap
at 17%, where a coarse sketch has the most room to differ.

### What the batching bought, and what it did not

Batching a level's histogram builds and subtractions into one launch each
(`27ab94d`) was predicted to be the largest of the four costs. That was **right
about the mechanism and wrong about its weight in most cases**:

- `depth 10` improved **3.3×**, from 17.05 s to 5.12 s. That is the case with
  by far the most nodes, and it is now the *best* row in the table rather than
  the worst. The per-node launch overhead was real and it dominated there.
- Everywhere else the gain is 1.0×–1.3×. Node counts are an order of magnitude
  lower, so there was much less launch overhead to remove.
- `depth 4` and `max_bin 64` came out **slower** (0.80× and 0.94×). These are
  single runs, so some of that is noise, but there is a plausible mechanism:
  the batched grid is sized for the *widest* node in the level and launched for
  every node, so a level mixing one large node with several small ones now
  starts blocks that exit immediately. Per-node launches were right-sized.
  Sizing the grid per node within the batch would fix it.

The flat ~5 s floor across most rows, largely independent of rows, features and
bins, says the remaining cost is **not** proportional to the work. That points
at the per-level host round trips rather than at the kernels.

### Where the time went then

1. **Three host round trips per level.** Down from five: the split evaluation
   now packs its results into two buffers, but each is still a full pipeline
   drain, and the partitioner reads its left counts for a third. Getting to one
   — or to none, by keeping the segment table on device — is the next thing to
   try, and the flat floor above is the evidence for it.
2. **The ELLPACK was uncompressed** when this was measured: four bytes per
   entry against XGBoost's bit-packed ~1 byte at 256 bins, so the hottest
   kernel moved 4× the memory it needed to, which is what should have mattered
   most at `rows 1M`, the row that improved least (1.01×). It is now
   bit-packed on device (`gpu::ellpack::pack_bins`, 8 bits for 256-bin data,
   9 with a missing sentinel) on every runtime with planes — but that has not
   been re-measured on a GPU yet, only tested for correctness at forced widths
   on the CPU runtime, where packing is deliberately off because it costs more
   instructions than it saves bytes there.
3. **The batched grid is sized for the widest node**, which costs the shallow
   cases (see `depth 4` above).

## Reproducing

```bash
tools/kaggle/cross-build.sh                               # Linux binaries into prebuilt/
tools/kaggle/push.sh --wait gpu-compare-metadata.json     # the T4 run; results in kaggle-output/
```

or, on a machine with a CUDA GPU:

```bash
cargo build --release --no-default-features --features cuda --bin train_bench
python tools/compare_gpu.py --binary target/release/train_bench
```

Add `--cpu` to time `device=cpu` alongside. Do not read CPU numbers from a
Colab VM: it has 2 vCPUs, so a CPU baseline there says more about the VM than
about either implementation. The same 2 vCPUs make a `--features cuda` build
take ~35 minutes, most of it in `tracel-rspirv` and `wgpu`.
