# GPU benchmark: `xgboost_rs` against XGBoost `gpu_hist`

Run on a Google Colab **Tesla T4** (15 GB, driver 580.82.07, 2 vCPU, 12 GB RAM),
XGBoost 3.4.0, `xgboost_rs` built `--release --features cuda`, via
`tools/compare_gpu.py`. Both sides train on the same generated bytes with the
same parameters; each trains once per case, because repeating the fit would let
XGBoost reuse the binned matrix it caches on the `DMatrix` while this crate
rebuilt it.

## Result

**This crate loses, by 8× to 17×.** `speedup` is XGBoost's time over ours, so
below 1.00 is a loss.

Accuracy is comparable throughout — train RMSE within ~2% of the reference,
and identical to 7e-5 on `lossguide`. The two sketch quantiles differently, so
exact agreement is not expected; `max_bin 64` is the widest gap at 17%, which
is where a coarse sketch has the most room to differ. The timings are therefore
measuring the same amount of work, and the loss is real rather than an artefact
of one side doing less.

## Where the time goes

Diagnosis from the code, ordered by expected size. None of these is a design
dead end; all are fixable without changing what the kernels compute.

1. **One launch per node, not per level.** `GpuHistGrower::build_children`
   issues a histogram build *and* a subtraction for every node. XGBoost batches
   a whole level into one kernel. This is why `depth 10` is the worst row in
   the table: going from depth 4 to depth 10 costs this crate 4.0× and XGBoost
   only 2.9×, and depth is what multiplies the node count.
2. **Five host round trips per level.** `SplitEvaluatorGpu::evaluate` reads
   back four separate buffers — four full pipeline drains — and
   `RowPartitioner::partition` reads the left counts for a fifth. At depth 10
   over 20 rounds that is ~1000 drains. The four reads should be one packed
   buffer, and the partitioner's counts can stay on device.
3. **A host-side zero buffer uploaded per batch.** `zeroed_frontier` builds
   `vec![0u32; n_bins * 4 * slots]` on the host and copies it across. At depth
   10 with 512 slots and 12800 bins that is ~105 MB per level. It should be a
   device-side fill.
4. **The ELLPACK is uncompressed.** Four bytes per entry against XGBoost's
   bit-packed ~1 byte at 256 bins, so the hottest kernel moves 4× the memory it
   needs to.
5. **The cut layout is re-uploaded per tree**, in `SplitEvaluatorGpu::new`.

## Reproducing

```bash
cargo build --release --features cuda --bin train_bench
python tools/compare_gpu.py --binary target/release/train_bench
```

Add `--cpu` to time `device=cpu` alongside. Do not read CPU numbers from a
Colab VM: it has 2 vCPUs, so a CPU baseline there says more about the VM than
about either implementation.
