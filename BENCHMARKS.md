# Measured performance

Two different questions, measured separately:

* **Against XGBoost** — is this crate faster than the thing it reimplements, on
  identical data and configuration? (`tools/compare.sh`)
* **Across parameters** — which parameters actually cost anything, and how
  much? (`src/bin/param_bench.rs`, whose doc comment carries the ratio table)

Absolute times are machine-dependent. The ratios are the point.

## Head to head against XGBoost 3.4.0 (CPU)

`tools/compare.sh 8`, 16-core box, 8 threads, best of 3 whole-process runs per
side. Both sides train on the same generated bytes: the Rust benchmark writes
the matrix once and the Python harness reads it back, so neither side is
timing a different dataset. Each run pays its own quantile sketch and binning
pass, so neither benefits from a cache the other cannot use.

`speedup > 1` means this crate is faster.

### Reading this

**At parity on the shallow dense depthwise cases** — 1.02x to 1.10x on four of
them, which is where most of the tuning has gone.

Three places where it loses badly, and they are the ones worth working on:

* **Sparse input, 4.3x slower** (0.23x). A 30%-sparse matrix at depth 6 costs
  2.06s against XGBoost's 0.47s — while the *same shape* under lossguide is
  only 0.80x. A cost that appears under one growth policy and not the other is
  a partitioning problem, not a histogram one.
* **Deep trees, 2.9x slower** (0.35x). Depth 6 -> 10 costs this crate 17.7x
  (0.187 -> 3.307) where it costs XGBoost 6.0x (0.193 -> 1.160). Something is
  superlinear in depth here that is not upstream.
* **lossguide, up to 2x slower**. Worst on the smallest case (0.50x at 100k
  rows), converging towards parity as rows grow — the signature of per-node
  overhead rather than per-row work.

### Caveat: the fits are not identical

`compare.sh` reports final train-rmse for both sides, and **no case matches**
to the 1e-5 bar — differences run from 0.1% to 4%. So these timings are not
strictly like-for-like: the two implementations are doing measurably different
work, and a speed number cannot be fully trusted until the fits agree.

This is the same divergence `tests/oracle_string_parameters.rs` tracks (64/94
cases match XGBoost 3.4.0 on tree structure). Correctness first, then speed —
optimising against a target you do not match is optimising the wrong thing.

## GPU

The CubeCL kernels (ELLPACK quantisation, per-node histogram build, the
subtraction trick) pass their full oracle — exact `i64` equality against a CPU
reference — on the local Vulkan/lavapipe runtime: `cargo test --features gpu
--test kernels`, 14/14.

They are **not yet wired into training**. `device=cuda` resolves to the
`grow_gpu_hist` updater, which `api::train_from` refuses rather than silently
training on the CPU. So there is no GPU training number to report yet, and the
crate does not currently ship a GPU fit.

For CUDA numbers see `KAGGLE.md`; note that Kaggle's **P100 is SM 6.0**, below
the SM70 XGBoost's own wheels require, so an XGBoost GPU baseline cannot be
measured on a P100 session — the CubeCL kernels compile through NVRTC for
whatever device is present and are unaffected.
